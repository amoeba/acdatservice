# ACSP per-setup bundle format

Version 1. Status: **draft** — the format is implemented and unit-tested in
[`src/setup_bundle.rs`](../src/setup_bundle.rs). It is generated by the
ac-noclip TypeScript generator and served at
`GET /dats/portal/setups/0x{id:08X}` from the R2 key
`portal/setups/0x{id:08X}.bin`.

## Why

Rendering a Setup requires its whole closure of portal DAT files — GfxObjs,
surfaces, palettes, textures, and so on. A single Setup references **15–167**
such files, most of them small. Fetching them one at a time turns a single
setup into dozens or hundreds of small requests, and the set of files is fixed
at generation time.

Packing the closure into one object per Setup turns that into a constant number
of requests and gives each setup a deterministic cache key:
`portal/setups/0x{id:08X}.bin`. Because the closure is computed from the
client's own data, the generator also knows which referenced ids are *not*
actually present in the DAT; those are recorded explicitly so a consumer can
distinguish “known missing” from “not part of this setup”.

The key is the Setup id alone. A DAT patch that changes a Setup's closure keeps
the id, so the pack must be regenerated and re-uploaded; because the route is
served `immutable`, bust the key (for example with a generation prefix) or purge
the cache when republishing after a patch.

This is the setup analogue of the ACLB per-landblock format documented in
[`docs/bundle-format.md`](./bundle-format.md).

## Conventions

- All integers are **little-endian**.
- File ids are unsigned 32-bit portal DAT ids.
- Offsets in this document are relative to the start of the file.
- A bundle describes exactly **one** Setup.
- A payload may be zero-length; that is distinct from a known-missing id.
- Writers SHOULD write entries in ascending id order. Readers MUST NOT assume
  any particular order.

## Layout

### Header — 16 bytes

| Offset | Size | Type  | Field      | Notes                                        |
| -----: | ---: | :---- | :--------- | :------------------------------------------- |
| `0x00` |    4 | bytes | `magic`    | `41 43 53 50` = ASCII `ACSP`                 |
| `0x04` |    1 | `u8`  | `version`  | `1`                                          |
| `0x05` |    1 | `u8`  | `kind`     | `3` = setup                                  |
| `0x06` |    2 | `u16` | `reserved` | must be `0`                                  |
| `0x08` |    4 | `u32` | `setup_id` | the Setup this closure belongs to            |
| `0x0C` |    4 | `u32` | `count`    | number of entries                            |

### Entry table — `count × 12` bytes

Immediately follows the header. One record per closure member. The table need
not be sorted, but writers SHOULD emit ascending ids.

| Offset | Size | Type  | Field    | Notes                                          |
| -----: | ---: | :---- | :------- | :--------------------------------------------- |
| `0x00` |    4 | `u32` | `id`     | full portal DAT file id                        |
| `0x04` |    4 | `u32` | `offset` | absolute file offset of this entry’s payload   |
| `0x08` |    4 | `u32` | `length` | payload length, or `0xFFFFFFFF` if missing     |

The offset is redundant with the on-disk packing order, but it lets a reader
build an index in one pass and then seek directly to any payload without
summing preceding lengths (random access).

### Missing marker

An entry whose `length == 0xFFFFFFFF` (the `MISSING` sentinel) is a
**known-missing id**: the closure references it, but the DAT has no such file.
It has **no payload**, contributes **no bytes** to the file, and its `offset`
field MUST be written as `0`. A decoder returns it as a present entry whose
data is `None` — this is not an error.

### Payloads

The present payloads immediately follow the entry table, packed back to back
with **no padding** or alignment. The first present payload starts at
`16 + 12 × count`. Every present payload is described by its entry’s absolute
`offset` and `length`. A zero-length present payload is valid and occupies the
cursor position without advancing it.

Total file size:

```
16 + (12 × count) + Σ (present payload lengths)
```

A bundle with `count = 0` is valid (a 16-byte header).

## Invariants

A decoder MUST reject a file that violates any of these:

1. Fewer than 16 bytes.
2. `magic != "ACSP"`.
3. `version != 1`.
4. `kind != 3`.
5. `reserved != 0`.
6. `count × 12` overflows `usize`, or the entry table extends past the end of
   the file.
7. Any present payload extends past the end of the file.
8. Any present payload `offset < 16 + 12 × count` (it points into the header or
   entry table).
9. The present payload ranges do not tile the bytes after the table exactly —
   that is, there is a gap, an overlap, or trailing bytes. Known-missing
   entries contribute no range.
10. The same id appears more than once.

A decoder MUST NOT assume the entry ids are contiguous, sorted, or a fixed
size; it must walk the table. The `offset` of a known-missing entry is ignored
by readers (writers MUST still write `0`).

## Worked example

A setup bundle with `setup_id = 1` and two entries:

| id           | payload | Notes        |
| :----------- | :------ | :----------- |
| `0x02000001` | `DE AD` | present      |
| `0x06000000` | —       | known missing |

```text
offset  bytes
0x0000  41 43 53 50   magic "ACSP"
0x0004  01            version 1
0x0005  03            kind = setup
0x0006  00 00         reserved
0x0008  01 00 00 00   setup_id = 1
0x000C  02 00 00 00   count = 2
0x0010  01 00 00 02   entry 0 id = 0x02000001
0x0014  28 00 00 00   entry 0 offset = 40
0x0018  02 00 00 00   entry 0 length = 2
0x001C  00 00 00 06   entry 1 id = 0x06000000
0x0020  00 00 00 00   entry 1 offset = 0
0x0024  FF FF FF FF   entry 1 length = MISSING
0x0028  DE AD         entry 0 payload
```

One line:

```text
41 43 53 50 01 03 00 00 01 00 00 00 02 00 00 00
01 00 00 02 28 00 00 00 02 00 00 00 00 00 00 06
00 00 00 00 FF FF FF FF DE AD
```

## Reference reader (pseudocode)

```text
read u32 magic; require magic == "ACSP"
read u8  version; require version == 1
read u8  kind;    require kind == 3
read u16 reserved; require reserved == 0
read u32 setup_id
read u32 count

payload_start = 16 + count * 12
entries = {}
ranges = []
repeat count times:
    read u32 id
    read u32 offset
    read u32 length
    require id not in entries
    if length == 0xFFFFFFFF:
        entries[id] = missing          # no payload, no range
    else:
        require payload_start <= offset
        require offset + length <= file_size
        entries[id] = bytes[offset .. offset + length]
        ranges.push((offset, offset + length))

# Present payload ranges must tile the payload region exactly: no gaps,
# overlaps, or trailing bytes. Known-missing entries contribute nothing.
require ranges.sorted() == tile(payload_start, file_size)
```

## Rust API

[`acdatservice::setup_bundle`](../src/setup_bundle.rs) is the shared
implementation:

```rust
use acdatservice::setup_bundle::{decode, encode, SetupBundle, SetupEntry};

let bundle = SetupBundle {
    setup_id: 1,
    entries: vec![
        SetupEntry { id: 0x0200_0001, data: Some(vec![0xDE, 0xAD]) },
        SetupEntry { id: 0x0600_0000, data: None }, // known missing
    ],
};
let bytes = encode(&bundle)?;
let parsed = decode(&bytes)?;

// None       = id absent from the bundle
// Some(None) = known missing
// Some(Some(bytes)) = present
assert_eq!(parsed.payload(0x0200_0001), Some(Some(&[0xDE, 0xAD][..])));
assert_eq!(parsed.payload(0x0600_0000), Some(None));
assert_eq!(parsed.payload(0x9999_9999), None);
```

## Serving

The ac-noclip TypeScript generator writes one object per Setup to R2 under
`portal/setups/0x{id:08X}.bin`. It is served by
`GET /dats/portal/setups/0x{id:08X}`.

## Versioning

Any layout change — new field, different framing, different membership — MUST
increment `version`. Decoders MUST reject unknown versions rather than guess.
There is no negotiation; the generator and its readers ship together.

## Non-goals

- No compression is applied by the format. Compress the whole object at rest /
  on the wire (gzip/brotli) if desired.
- This format only covers portal DAT setup closures. It does not describe how
  the closure is computed, nor does it carry metadata beyond the member ids.
